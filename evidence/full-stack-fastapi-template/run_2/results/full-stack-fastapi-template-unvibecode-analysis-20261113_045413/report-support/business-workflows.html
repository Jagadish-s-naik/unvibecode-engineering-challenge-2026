Workflow 1

Manage items

What this workflow does

An authenticated current_user creates, retrieves, updates, or deletes Item records; non-superusers are limited to items they own for reads and mutations by item ID.

Purpose

Create and manage items, or retrieve them

What it produces

Item

Who relies on it

current_user; Item.owner_id identifies the owning user

Why this workflow matters

  • Item data is persisted or returned to the caller
  • Deleting an item removes its database record

Delete an item

What this workflow does

A user selects Delete Item from the row action menu, confirms in a dialog, and the frontend calls ItemsService.deleteItem with the supplied item ID; success closes the dialog and invokes the parent callback.

Purpose

Permanently delete a selected item

What it produces

Item

Why this workflow matters

  • Requests item deletion through the API.
  • The dialog warns that deletion is permanent and cannot be undone.

Admin UI user management

What this workflow does

An admin UI user submits a form or deletion confirmation, which calls the generated UsersService client for a user mutation; server-side handling is not included here.

User

Who relies on it

The user being managed; identity and authorization of the operator are not established by this fragment.

Why this workflow matters

  • User create, update, and delete operations are requested through the generated API client.
  • A database mutation is not confirmed by the supplied frontend and API-contract evidence.
